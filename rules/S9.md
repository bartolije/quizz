# Session 9 — Déploiement (Railway, un seul service)

> **Mis à jour après coup :** le plan initial prévoyait le jeu sur Vercel + le
> serveur sur Railway. En pratique on a simplifié en **un seul service Railway**
> qui sert TOUT (jeu + API + WebSocket). Ce document décrit ce qui est réellement
> en place. Guide pas à pas, sans pré-requis technique.

---

## 1. Le principe (en 30 secondes)

Un seul programme tourne sur **Railway** et fait tout :
- il sert le **jeu** (React) — host, TV, téléphones ;
- il gère l'**API** (créer une session, éditer les quiz) ;
- il gère le **temps réel** (WebSocket : réponses, scores).

→ Une seule URL, ex. `https://lya-quizserver-production.up.railway.app`.
Pas de cross-domaine, pas de 2ᵉ hébergeur, pas de variable d'URL à régler.

| Qui | Adresse |
|---|---|
| Admin — créer/éditer les quiz | `…/admin` |
| Toi — écran de contrôle | `…/host/control` |
| Toi — écran TV (vidéoproj) | `…/host/display` |
| Joueurs (téléphones) | QR code → `…/join?pin=XXXX` |

---

## 2. Mettre en ligne (déjà fait, pour mémoire)

1. **railway.app** → **New Project** → **Deploy from GitHub repo** → `bartolije/quizz`.
2. Railway lit `railway.json` et build/lance tout seul (build du shared + client + serveur, start `node packages/server/dist/index.js`).
3. Service → **Settings → Networking → Generate Domain** → l'URL publique.
4. Vérifier : `…/health` → `{"status":"ok"}`.

**Déploiement automatique** : chaque `git push` sur `main` redéploie tout seul.

---

## 3. Les 2 réglages qui rendent l'app complète

### a) Disque persistant (sinon les quiz disparaissent au redeploy)
- Service `lya-quizserver` → **+ Create → Volume** (mount path : peu importe, ex. `/data`).
- Le serveur détecte automatiquement le volume (`RAILWAY_VOLUME_MOUNT_PATH`) et y range la base SQLite. Rien d'autre à configurer.

### b) Mot de passe de l'éditeur
- Service → **Variables** → `ADMIN_PASSWORD` = (ton mot de passe).
- Protège `…/admin` (sinon valeur par défaut publique).

> Variables optionnelles : `LOG_LEVEL` (défaut `info`), `DATABASE_PATH` (override manuel du chemin DB).

---

## 4. Tester en ligne

1. `…/admin` → mot de passe → crée un quiz (3 types possibles) → **Lancer**.
2. L'écran de contrôle s'ouvre avec un PIN + QR.
3. `…/host/display` sur la TV.
4. Téléphone : scan du QR → pseudo → joue.
5. Le quiz créé persiste (volume) → toujours là après un redeploy.

---

## 5. Quoi regarder / déboguer (cf. S10)

- **Logs** : Railway → service → **Deployments → View Logs**. Cherche un nom
  d'événement (`question_closed`, `client_error`…) ou un `sessionId` pour
  rejouer une partie. Les erreurs des téléphones remontent en `client_error`.
- **Santé** : `…/health` → `{"status":"ok"}`.

---

## 6. À savoir

- **L'état d'une partie est en mémoire** : un redeploy (ou une veille) **réinitialise
  les parties/scores en cours** — mais **pas les quiz** (eux sont en base sur le
  volume). Évite de redéployer en pleine partie.
- Un seul serveur (parfait pour 15-30 joueurs internes), pas de mise à l'échelle
  multi-instances.
- Coût : Railway ≈ 5 $/mois.
