# Session 3 — Host UI : /host/control + /host/display + QR code

## Contexte

S1 et S2 sont terminées. Le join participant fonctionne, le lobby est vivant,
la reconnexion est validée. On attaque maintenant les deux vues host.

Ne pas modifier `packages/shared/`. Ne pas modifier la logique de join participant.
Tous les imports depuis `@lya-quiz/shared`.

---

## Objectif de S3

À la fin de cette session :

1. Le host ouvre `/host/control` → une session est créée automatiquement,
   un PIN s'affiche, un QR code pointe vers la page join des participants
2. Le host ouvre `/host/display` sur un second écran → vue synchronisée
   en temps réel avec `/host/control`
3. Le host voit les participants arriver dans les deux vues
4. Le host peut lancer le quiz (bouton "Démarrer") — pour l'instant ça
   change juste le statut de session à `running`, les questions viennent en S4
5. Les deux vues host sont synchronisées via Socket.io (même room)

---

## Comportement attendu

### `/host/control` (écran Mac du host)

- Au chargement : appel `POST /api/sessions` → reçoit `{ pin, sessionId }`
- Connexion Socket.io avec `host_join` → rejoint la room de la session
- Affiche :
  - Le PIN en grand
  - Le QR code pointant vers `https://[domaine]/join?pin=XXXX`
  - La liste des participants connectés (temps réel)
  - Le nombre de participants
  - Un bouton "Démarrer le quiz" (disabled si 0 participants)
  - Un aperçu de la prochaine question (titre + type) — stub pour l'instant,
    sera branché sur la DB en S8
- Reçoit `participant_joined` et `participant_left` → met à jour la liste

### `/host/display` (écran TV)

- Au chargement : lit le `sessionId` depuis `localStorage` ou un paramètre URL
- Se connecte à la même room Socket.io que `/host/control`
- Affiche en grand :
  - Le PIN
  - Le QR code
  - La liste des participants (avatars ou pseudos en grille)
  - "En attente du host..." tant que le quiz n'a pas démarré
- Doit être lisible à 3-4 mètres (grande police, contraste fort)
- Cette vue est passive : elle ne peut rien déclencher, elle affiche seulement

### Synchronisation des deux vues host

Les deux vues sont dans la même room Socket.io `host:{sessionId}`.
Quand un participant rejoint, les deux vues se mettent à jour simultanément.
Pas de polling, pas de fetch — uniquement Socket.io.

## Contraintes techniques

### QR code

Utiliser la librairie `qrcode` (npm : `qrcode` + `@types/qrcode`).
Générer le QR code côté client en canvas ou SVG.
L'URL encodée dans le QR : `window.location.origin + '/join?pin=' + pin`
Ainsi en dev c'est `http://192.168.x.x:5173/join?pin=XXXX` et en prod
c'est `https://quizz.jbartoli.fr/join?pin=XXXX` — automatique.

### Création de session au chargement de /host/control

```
1. Vérifier localStorage['lya_host_session'] (sessionId + pin)
2. Si présent : tenter de rejoindre cette session via host_join
3. Si absent ou session expirée : POST /api/sessions → stocker dans localStorage
4. Connecter le socket et émettre host_join avec le pin
```

Ce mécanisme évite de créer une nouvelle session si le host rafraîchit la page.

### /host/display doit trouver la session

Deux options possibles, implémenter les deux :
- `localStorage['lya_host_session']` (même navigateur/profil)
- Paramètre URL : `/host/display?session=XXXX` (autre navigateur ou autre machine)

### Routing

Ajouter react-router-dom v6 au client. Routes :
- `/` ou `/join` → JoinPage
- `/lobby` → LobbyPage (redirection automatique après join)
- `/host/control` → HostControlPage
- `/host/display` → HostDisplayPage

Mettre à jour `App.tsx` pour utiliser `<BrowserRouter>` et `<Routes>`.
Mettre à jour `vite.config.ts` : ajouter `historyApiFallback` pour que
le routing côté client fonctionne sur refresh.

### Côté serveur : rien de nouveau

Le serveur gère déjà `host_join` depuis S2. Vérifier seulement que :
- La room `host:{sessionId}` reçoit bien `participant_joined` et `participant_left`
- `POST /api/sessions` retourne bien `{ pin, sessionId }`

Si ce n'est pas le cas, corriger dans `src/handlers/join.ts` :
le broadcast `participant_joined` doit aller à `io.to(session.id)` ce qui
inclut déjà les hosts (qui sont dans la room `session.id`).

## Checklist de validation

### Test 1 — Création de session
```
1. Ouvrir http://localhost:5173/host/control
2. Un PIN à 4 chiffres s'affiche
3. localStorage contient 'lya_host_session'
4. Rafraîchir la page → même PIN (pas de nouvelle session créée)
```

### Test 2 — QR code fonctionnel
```
1. Scanner le QR code avec un téléphone
2. L'URL ouverte doit être http://[IP_LOCAL]:5173/join?pin=XXXX
3. Le PIN doit être pré-rempli dans la JoinPage (lire le ?pin= de l'URL)
```

### Test 3 — Synchronisation temps réel
```
1. Ouvrir /host/control dans un onglet
2. Ouvrir /host/display dans un autre onglet
3. Rejoindre avec un téléphone
4. Le participant apparaît dans les DEUX vues simultanément
```

### Test 4 — /host/display via URL param
```
1. Copier le sessionId depuis localStorage
2. Ouvrir /host/display?session=XXXX dans un navigateur différent
3. Doit afficher le même PIN et la même liste de participants
```

### Test 5 — Bouton Démarrer
```
1. Rejoindre avec au moins 1 participant
2. Le bouton "Démarrer" devient actif
3. Cliquer → host_start_quiz émis
4. Le statut de session passe à 'running' côté serveur
5. (les questions arrivent en S4, pour l'instant juste valider l'event)
```
