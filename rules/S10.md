# Session 10 — Observabilité : logs structurés + capture d'erreurs (fiabilisation & retours live)

## Contexte

Le jeu est déployé (S9 : jeu sur Vercel, serveur sur Railway). Quand tu vas
**tester en live** et récolter des retours, il faut pouvoir **comprendre ce qui
se passe et déboguer vite** — surtout les bugs côté **téléphone des joueurs**,
aujourd'hui totalement invisibles depuis le serveur.

**Ce qui existe déjà :** le serveur tourne avec le logger Fastify (pino) → il
écrit en JSON sur la sortie standard, que **Railway capture** (onglet
*Deployments → View Logs*). On part de là et on le **muscle**.

### Décisions actées

- **Logs** : on reste sur **Railway + logs structurés** (pas de Sentry pour
  l'instant — réévaluable en S10.b si le besoin se confirme).
- **Erreurs joueur** : **oui**, les erreurs JS du téléphone sont **renvoyées au
  serveur** et loggées.
- **Bouton feedback in-app** : **non** (retours collectés autrement).
- **Alerte uptime** : **non** pour l'instant.

---

## Objectif de S10

À la fin :

1. Chaque **événement métier** important est loggé de façon **structurée**, avec
   le contexte utile (`sessionId`, `pin`, `participantId`, `questionIndex`…), pour
   pouvoir reconstituer une partie a posteriori.
2. Le serveur **ne crashe plus silencieusement** : toute exception dans un
   handler est attrapée, loggée avec son contexte, et n'abat pas le process.
3. Les **erreurs côté joueur** (crash JS, promesse rejetée, erreur React)
   remontent au serveur et apparaissent dans les logs Railway.
4. On sait **où regarder et comment filtrer** dans Railway (documenté).

---

## Ce qu'on construit

### 1. Serveur — logger structuré par événement (`src/logger.ts`)

Un petit module pino (réutilise la conf Fastify) exposant un `log` partagé.
Helper `logEvent(evt, fields, msg?)` pour une forme homogène :

```
log.info({ evt: 'question_started', sessionId, pin, questionIndex, total }, 'question started')
```

**Taxonomie d'événements** (champ `evt`) à couvrir :

| `evt` | Champs clés |
|---|---|
| `session_created` | sessionId, pin |
| `host_joined` | sessionId, pin, socketId |
| `participant_joined` / `participant_rejoined` | sessionId, pin, participantId, pseudo |
| `participant_left` | sessionId, participantId |
| `quiz_started` | sessionId |
| `question_started` | sessionId, questionIndex, total, type, timeLimit |
| `answer_received` | sessionId, participantId, answeredCount, totalCount |
| `question_closed` | sessionId, questionIndex, answeredCount, correctCount, closeReason (timer/all_answered) |
| `quiz_ended` | sessionId, participants, topScore |
| `client_error` | (cf. §3) |
| `handler_error` | event, err.message, err.stack, socketId |
| `fatal` | uncaughtException / unhandledRejection |

> Niveaux : `info` (vie normale), `warn` (anomalie récupérable : token invalide,
> réponse hors question), `error` (handler_error, client_error), `fatal`.
> Niveau pilotable par `LOG_LEVEL` (défaut `info`).

### 2. Serveur — robustesse des handlers

- Envelopper chaque handler socket (`join`, `rejoin`, `host_join`,
  `host_start_quiz`, `host_next_question`, `submit_answer`, `disconnect`) dans un
  `try/catch` qui logge `handler_error` (event + contexte) et, si pertinent, émet
  `quiz_error { code: 'UNKNOWN' }` au socket — **sans faire tomber le serveur**.
- `process.on('uncaughtException')` et `process.on('unhandledRejection')` →
  logguent `fatal` (au lieu d'un crash muet). On laisse Railway redémarrer si
  besoin (restartPolicy déjà en place via `railway.json`).
- Optionnel : `io.engine.on('connection_error', …)` pour tracer les échecs de
  handshake WebSocket.

### 3. Client — remontée des erreurs au serveur

- **Endpoint REST** `POST /api/client-log` (pas un event socket : doit marcher
  même quand le socket ne se connecte pas). Body :
  `{ level, message, stack?, context: { path, pin?, participantId?, ua } }`.
  Le serveur logge `{ evt: 'client_error', ... }`. **Garde-fous** : taille de body
  limitée, pas de log du log (éviter les boucles), throttle simple côté client.
- **Côté client** (`src/error-reporting.ts`) :
  - `window.addEventListener('error', …)` et `'unhandledrejection'` → POST via
    `apiUrl('/api/client-log')` (la base serveur de S9).
  - Un **React ErrorBoundary** autour de `<App/>` qui logge le crash et affiche
    un écran « Oups, recharge la page » au lieu d'un écran blanc.
  - Contexte joint : `location.pathname`, `pin`/`participantId` depuis le store si
    dispo, `navigator.userAgent` (pour savoir quel type de téléphone casse).

### 4. Doc — « où regarder »

Section dans `S10.md` / README : ouvrir Railway → Logs, **filtrer par `evt`**
(ex. taper `client_error` ou un `sessionId` dans la recherche), lire les champs.

## Ce qu'on regarde (Railway)

- `evt: question_closed` avec `closeReason` → comprendre pourquoi une question
  s'est fermée (temps écoulé vs tous répondu).
- `evt: client_error` → les bugs réels rencontrés par les joueurs, avec le modèle
  de téléphone (userAgent) et la page.
- `evt: handler_error` / `fatal` → ce qui casse côté serveur, avec la pile.
- Filtrer par `sessionId` pour rejouer une partie entière dans l'ordre.

---

## Checklist de validation

1. Lancer une partie complète → la séquence d'`evt` apparaît dans les logs, dans
   l'ordre, avec `sessionId`/`pin`.
2. Provoquer une erreur dans un handler (test) → `handler_error` loggé **et le
   serveur reste debout** (les autres joueurs continuent).
3. Déclencher une erreur JS côté client (test) → `client_error` visible dans les
   logs serveur avec `path` + `userAgent`.
4. Faire planter un composant React → l'ErrorBoundary affiche l'écran de secours
   (pas d'écran blanc) et logge l'erreur.
5. `question_closed` indique le bon `closeReason` selon le scénario.
